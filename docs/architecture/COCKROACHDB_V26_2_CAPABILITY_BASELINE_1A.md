# CockroachDB v26.2 Capability Baseline 1A

## 1. Purpose and status

This document records the Step 3 live capability baseline for the later Memory
Patch persistence architecture. It is a capability spike, not a production
database design: no production schema, migration, persistence adapter,
authorization service, changefeed consumer, or retry middleware was created.

The evidence set contains 36 mandatory capability rows:

- `34 PASS`;
- `0 FAIL`;
- `2 DEFER`;
- overall decision: `PINNED_WITH_EXPLICIT_DEFERRED_ITEMS`.

The two deferred rows are:

- `CRDB-030` — a natural contention workload did not expose a client-visible
  `40001` within 10 bounded attempts because both transactions completed;
- `CRDB-035` — TTL and changefeeds passed independently, but a combined
  TTL-generated delete stream was not forced in this bounded run.

## 4. Evidence standard and decision taxonomy

Three evidence categories were kept separate:

1. **Official-source evidence** established release identity, support status,
   documented syntax, prerequisites, maturity where explicitly stated, and
   known limitations. Documentation alone never produced a capability PASS.
2. **Live-runtime evidence** established the actual build, cluster version,
   SQL semantics, result ordering, SQLSTATE values, isolation, catalog state,
   asynchronous behavior, and cleanup on the exact pinned runtime.
3. **Offline repository evidence** established deterministic serialization,
   schema completeness, digest validation, redaction, bounded retry behavior,
   loopback guards, resource ownership, link validity, and ordinary-test
   isolation from live execution.

Primary status meanings:

- `PASS` — the required semantics were observed on the exact live runtime, or
  the expected safe rejection occurred;
- `FAIL` — prerequisites were satisfied but required live behavior
  reproducibly did not occur;
- `DEFER` — a trustworthy decision could not be completed within a real,
  explicitly recorded boundary.

MVP decisions are independent of the primary result:

- `USE` — suitable as a later design input under normal contract validation;
- `USE_WITH_GUARD` — usable only with the listed operational or security
  boundary;
- `DEFER` — not an MVP dependency until the deferred evidence is completed;
- `DO_NOT_USE` — excluded. No matrix row received this value, although several
  unsafe interpretations and unsupported paths are explicitly excluded below.

`UNKNOWN` maturity means the consulted official record did not supply a
maturity label that the spike could safely normalize. It does not mean the
feature was absent, and live PASS does not manufacture a maturity claim.

## 6. Feature suitability and limitations

### Approved for later design

The `USE` rows are:

`CRDB-001`–`CRDB-007`, `CRDB-011`–`CRDB-017`, `CRDB-020`,
`CRDB-021`, `CRDB-026`, `CRDB-027`, `CRDB-029`, `CRDB-032`, and
`CRDB-036`.

They establish the exact runtime identity, scalar vector behavior, English and
German full-text behavior, basic RLS tenant isolation, TTL definition and job
registration, partial uniqueness, serializable baseline, retry classification,
and owned cleanup.

### Approved only with guards

The `USE_WITH_GUARD` rows are:

`CRDB-008`–`CRDB-010`, `CRDB-018`, `CRDB-019`, `CRDB-022`–`CRDB-025`,
`CRDB-028`, `CRDB-031`, `CRDB-033`, and `CRDB-034`.

Their guards are binding:

- build vector indexes before bulk data load where possible; v26.2
  documentation warns that non-empty-table backfill blocks writes;
- distinguish index existence, eligibility, optimizer selection, and
  approximate-result quality;
- treat tenant/HAT prefix columns only as filtering and index dimensions;
- use FORCE RLS intentionally and test table-owner, ordinary-role, and admin
  behavior separately;
- assume root/admin and documented administrative operations sit outside the
  ordinary RLS boundary;
- treat TTL execution as asynchronous;
- give changefeed consumers independent tenant validation, deduplication,
  ordering, and at-least-once handling;
- keep AOST reads inside retained MVCC history and never substitute them for
  durable audit storage;
- use synthetic `40001` injection only for signal/classifier tests, never as
  evidence of a realistic contention rate.

### Deferred

- `CRDB-030` must be revalidated on a production-like multi-session or
  multi-node plane if Step 4 or later code needs a natural client-visible
  contention trace. This does not weaken the verified `40001` classifier.
- `CRDB-035` must be revalidated as a combined TTL-generated delete plus
  changefeed stream before any design depends on those delete events.

## 7. Critical cross-feature interactions

### Vector prefix versus authorization

The live index accepted exact `tenant_id` and `hat_id` prefix columns and the
filtered query returned only the selected prefix. A privileged query without
those predicates saw both tenants. Prefixes improve eligibility and constrain
the query; they do not authenticate a caller or authorize access. Step 4 must
combine them with RLS or an equivalent real security boundary.

### RLS versus changefeeds

The live CDC query against an RLS table failed with `0A000`. Official v26.2
documentation also states that emitted changefeed messages are not filtered by
RLS. A changefeed transport and every downstream consumer therefore need an
independent tenant-safe contract. RLS success on OLTP sessions cannot be cited
as CDC isolation.

### FORCE RLS, ownership, and administration

The table owner saw two rows before FORCE and zero afterward because it had no
matching tenant context. Ordinary roles did not bypass the policy; root/admin
did. Constraints, `TRUNCATE`, backup/restore, logical data replication, and
physical cluster replication are documented non-policy or bypass boundaries.
Step 4 must use least-privileged application roles and must test owner and FORCE
semantics explicitly.

### TTL versus changefeeds

TTL DDL, job registration, physical deletion, and explicit changefeed CRUD
events each passed. The combined TTL-generated delete event was not forced and
remains `DEFER`. Official behavior says TTL deletes can produce change events
unless disabled, but production design must not depend on that interaction
until it is revalidated together.

### AS OF SYSTEM TIME versus garbage collection

The captured historical read returned `v1` after the current value became
`v2`, and a future-invalid timestamp failed with `22023`. The result exists
only while MVCC history remains inside the GC retention window. AOST is a
bounded historical-read tool, not unlimited history, an audit ledger, or a
backup.

### Vector-index backfill versus writes

The probe created the vector index on an empty table before loading fixtures.
This avoided the documented v26.2 non-empty-table backfill write block. Step 4
must plan vector indexes before bulk load or use an explicit, reviewed
maintenance/backfill procedure; it must not infer online backfill safety from
this empty-table proof.

### Partial uniqueness versus retries

The active duplicate produced `23505`; the retry injector produced `40001`.
They are distinct outcomes. A permanent uniqueness violation must not enter the
serializable retry loop merely because both can arise during a write.

## 8. Security boundaries

The spike proved structural database behavior, not application authority.
Step 4 and later layers must preserve all of these boundaries:

- authenticated identity and authorization must be established before setting
  database role or tenant context;
- tenant context must not be caller-controlled unverified text;
- RLS policy predicates and `WITH CHECK` must cover read and write paths;
- FORCE RLS does not remove the separate root/admin boundary;
- table owners, migrations, backup/restore, replication, constraints, and
  truncation require separate threat analysis;
- vector and full-text filters are retrieval constraints, not authorization;
- changefeed records require tenant-safe envelopes and consumers because RLS
  does not filter the transport;
- the insecure runtime used here is permitted only for loopback-bound,
  disposable synthetic testing;
- no feature result grants a model, HAT, critic event, or serialized payload
  authority to approve or commit a memory patch.

## 9. Persistence boundaries

This baseline confirms capability primitives, but it does not implement or
prove:

- the production logical schema or migrations;
- authenticated human identity;
- production role provisioning and authorization;
- durable approval consumption or commitment idempotency;
- production uniqueness and optimistic-concurrency rules;
- distributed transaction behavior under realistic contention;
- durable audit storage or backup/restore correctness;
- changefeed consumer ordering, deduplication, checkpointing, or replay safety;
- production TTL service-level objectives;
- embedding generation or vector-retrieval quality;
- German-law retrieval recall, precision, freshness, or legal correctness;
- multi-node, multi-region, upgrade, failover, or cloud deployment behavior.

The capability results are inputs to those later designs, not substitutes for
them.

## 10. Binding Step 4 constraints

### Mandatory

1. Pin every Step 4 runtime and migration check to CockroachDB `v26.2.4`;
   reject `latest`, version ranges, and silent patch/minor upgrades.
2. Keep SERIALIZABLE as the project baseline. Classify retryability from exact
   SQLSTATE `40001`, cap attempts and backoff, close/rollback before sleeping,
   and never retry `23505` blindly.
3. Design tenant tables with explicit tenant scope and apply RLS read/write
   policies plus `WITH CHECK`; test distinct ordinary roles, table owner before
   and after FORCE, and admin boundaries.
4. Treat vector prefix columns as performance/filter keys only. Authorization
   must come from verified identity plus RLS or an equivalent boundary.
5. Keep CDC outside the RLS trust claim. Any later changefeed envelope,
   consumer, or outbox must enforce tenant scope independently and tolerate
   at-least-once delivery.
6. Use partial unique indexes only with explicit tenant keys and predicates;
   preserve the difference between current/active uniqueness and historical
   rows.
7. Treat TTL as asynchronous and AOST as GC-window-bounded. Neither is durable
   audit storage.
8. Re-run migration and policy tests on a production-like cluster before
   deployment; this single-node evidence is not a distributed guarantee.

### Guarded

1. Vector indexes may be designed because the v26.2 feature is GA and passed
   live, but create them before bulk load where possible and plan non-empty
   backfill as a maintenance event.
2. English and German full-text primitives may be used, but German dictionary
   stemming is not evidence of legal-domain ranking quality.
3. FORCE RLS may be used only with explicit role ownership and catalog tests.
4. TTL physical deletion may be used only with observability and a
   non-synchronous product contract.
5. Sinkless changefeed findings may inform CDC design, but production sinks and
   consumers require separate deployment, licensing, security, and durability
   validation.
6. AOST may support bounded diagnostics or temporal reads, with retained-history
   failures handled explicitly.
7. Synthetic retry injection may remain an offline/live test mechanism, never a
   production transaction mechanism.

### Deferred

1. Natural client-visible `40001` behavior under representative distributed
   contention.
2. Combined TTL-generated delete delivery through a changefeed.
3. External changefeed sinks, managed-cloud behavior, multi-node failover,
   multi-region latency, and production-load optimizer choices.

### Excluded

1. `latest`, silent series/patch upgrades, or an unverified CockroachDB binary.
2. `websearch_to_tsquery` on v26.2; the live runtime returned `0A000`.
3. Using vector prefixes, full-text predicates, ownership labels, or model
   output as authorization.
4. Claiming RLS automatically protects changefeed output.
5. Treating AOST as permanent history or TTL as synchronous deletion.
6. Retrying `23505` as though it were `40001`.
7. Depending on the session-only retry injector in production.
8. Inferring distributed or production behavior solely from this local
   single-node spike.
